# 低内存卡顿优化

64MB 内存下，策略要和普通 128MB/256MB 完全不一样：**水线不能留太大，否则容易 OOM；但也不能只剩 1MB，否则 direct reclaim 会卡死。**

对你这种 64MB、Linux 5.10、低内存回收卡顿的场景，我建议按下面这套来做。

---

# 一、最优先：打开 ZRAM

64MB 内存没有真正的“富余内存”，如果没有 swap，匿名页根本回收不动，系统会反复扫描 LRU，表现为：

- `kswapd` 忙；
- `kworker` 忙；
- 应用点击/启动卡顿；
- `/proc/vmstat` 里 `allocstall`、`pgscan_direct` 增长很快。

所以最实际的内核选项是：

```text
CONFIG_SWAP=y

CONFIG_ZRAM=y
CONFIG_ZSMALLOC=y
CONFIG_ZPOOL=y

CONFIG_CRYPTO_LZO=y
CONFIG_CRYPTO_LZ4=y
```

如果是 `make menuconfig`：

```text
General setup --->
    [*] Support for paging of anonymous memory (swap)

Device Drivers --->
    Block devices --->
        <*> Compressed RAM block device (ZRAM)
```

64MB 内存下，**强烈建议用 zram，而不是真实 flash swap**。  
真实 swap 写 eMMC/SD/NAND 可能又慢又伤寿命，zram 更适合。

---

# 二、64MB 推荐的 zram 配置

不要给太大，否则 zram 自己也可能占掉不少内存。

建议先从：

```bash
modprobe zram num_devices=1

# 如果之前已经配置过，先重置
swapoff /dev/zram0 2>/dev/null
echo 1 > /sys/block/zram0/reset

# 压缩算法，优先 lz4，没有就 lzo
echo lz4 > /sys/block/zram0/comp_algorithm
# 或者：
# echo lzo > /sys/block/zram0/comp_algorithm

# CPU 很弱就 1，双核/四核可以 2
echo 1 > /sys/block/zram0/max_comp_streams
# 或者：
# echo 2 > /sys/block/zram0/max_comp_streams

# 64MB 内存，建议先 24MB 或 32MB 逻辑大小
echo $((24*1024*1024)) > /sys/block/zram0/disksize
# 如果还不够，再试 32MB：
# echo $((32*1024*1024)) > /sys/block/zram0/disksize

# 如果你的内核支持 mem_limit，建议限制 zram 实际占用
echo $((12*1024*1024)) > /sys/block/zram0/mem_limit
# 或者 16MB：
# echo $((16*1024*1024)) > /sys/block/zram0/mem_limit

mkswap /dev/zram0
swapon -p 100 /dev/zram0
```

确认：

```bash
swapon -s
cat /proc/swaps
cat /sys/block/zram0/mm_stat
```

如果有 `zramctl`：

```bash
zramctl /dev/zram0
```

重点看：

```text
orig_data_size
compr_data_size
mem_used_total
mem_limit
```

# 三、64MB 的 sysctl 推荐参数

你之前说“剩下 1M 才触发回收”，这个太低了。  
64MB 下我建议先这样：

```bash
sysctl -w vm.min_free_kbytes=2048
sysctl -w vm.watermark_scale_factor=200
sysctl -w vm.swappiness=80
sysctl -w vm.page-cluster=0
sysctl -w vm.dirty_background_bytes=1048576
sysctl -w vm.dirty_bytes=4194304
```

含义：

| 参数                        | 64MB 建议 | 说明                                         |
| --------------------------- | --------: | -------------------------------------------- |
| `vm.min_free_kbytes`        |    `2048` | 保留约 2MB 最小空闲内存，避免只剩 1MB 才回收 |
| `vm.watermark_scale_factor` |     `200` | 约 2%，让 `kswapd` 更早醒来后台回收          |
| `vm.swappiness`             |      `80` | 配合 zram 更积极换出匿名页                   |
| `vm.page-cluster`           |       `0` | zram 不需要传统磁盘 swap 的大预读            |
| `vm.dirty_background_bytes` | `1048576` | 脏页约 1MB 就开始后台回写                    |
| `vm.dirty_bytes`            | `4194304` | 脏页最多约 4MB，避免低内存时集中写盘卡死     |

如果系统还是卡，可以继续微调：

```bash
sysctl -w vm.min_free_kbytes=3072
sysctl -w vm.watermark_scale_factor=300
sysctl -w vm.swappiness=100
```

但是如果出现更容易 OOM，就要降回去：

```bash
sysctl -w vm.min_free_kbytes=1024
sysctl -w vm.watermark_scale_factor=100
sysctl -w vm.swappiness=60
```

# 四、持久化配置

如果系统支持 `/etc/sysctl.conf`，可以写入：

```text
vm.min_free_kbytes = 2048
vm.watermark_scale_factor = 200
vm.swappiness = 80
vm.page-cluster = 0
vm.dirty_background_bytes = 1048576
vm.dirty_bytes = 4194304
```

如果支持 `/etc/sysctl.d/`，可以写：

```bash
cat > /etc/sysctl.d/99-lowmem.conf <<'EOF'
vm.min_free_kbytes = 2048
vm.watermark_scale_factor = 200
vm.swappiness = 80
vm.page-cluster = 0
vm.dirty_background_bytes = 1048576
vm.dirty_bytes = 4194304
EOF
```

然后：

```bash
sysctl --system
```

或者简单系统直接：

```bash
sysctl -p /etc/sysctl.conf
```

# 五、如果你的 5.10 有 MGLRU，打开它

如果你的 5.10 是厂商内核、Android/GKI backport 内核，可能会带 MGLRU。

检查是否有：

```text
CONFIG_LRU_GEN=y
CONFIG_LRU_GEN_ENABLED=y
CONFIG_HAVE_ARCH_PARENT_PMD_YOUNG=y
```

如果有，建议打开：

```text
CONFIG_LRU_GEN=y
CONFIG_LRU_GEN_ENABLED=y
```

运行时如果存在这个节点，也可以确认：

```bash
cat /sys/kernel/mm/lru_gen/enabled
```

如果没有这个选项，说明你的主线 5.10 没有 MGLRU，不能强开。

# 六、64MB 下不要打开的内核选项

这些会明显加重内存回收和系统卡顿，量产不要开：

```text
CONFIG_DEBUG_VM=y
CONFIG_DEBUG_PAGEALLOC=y
CONFIG_PAGE_OWNER=y
CONFIG_KASAN=y
CONFIG_LOCKDEP=y
CONFIG_PROVE_LOCKING=y
CONFIG_SHRINKER_DEBUG=y
CONFIG_MEMCG_DEBUG=y
CONFIG_DEBUG_LIST=y
CONFIG_DEBUG_SLAB=y
CONFIG_DEBUG_SLUB=y
```

另外，64MB 下建议关闭透明大页：

```text
# CONFIG_TRANSPARENT_HUGEPAGE is not set
```

透明大页会增加内存碎片整理和分配延迟，小内存嵌入式设备通常不适合。

# 七、如果 kworker 是 kcompactd，可以再调这个

如果你看到忙的 kworker 是：

```bash
ps | grep kcompactd
```

或者：

```bash
cat /proc/$(pidof kcompactd)/stack
```

说明可能还叠加了内存压缩/碎片整理压力。

64MB 下可以先关闭 proactive compaction：

```bash
sysctl -w vm.compaction_proactiveness=0
```

如果内核没有这个参数，也没关系。

如果你明确系统没有高阶内存分配需求，比如没有摄像头、显示、DMA 需要连续大块内存，可以在内核配置里评估：

```text
CONFIG_COMPACTION
CONFIG_CONTIG_ALLOC
CONFIG_CMA
```

但注意：**不要盲目关闭 CMA/COMPACTION**，很多显示、相机、GPU、DMA 驱动需要它。

---

# 八、检查 CMA 是否预留过大

64MB 总内存下，如果 CMA 预留太大，会非常痛。

查看内核启动参数：

```bash
cat /proc/cmdline
```

看有没有：

```text
cma=
```

也看内核配置：

```text
CONFIG_CMA_SIZE_MBYTES
```

如果你的系统没有大量连续内存需求，CMA 不要给太大。  
比如 64MB 系统，CMA 给 8MB/16MB 都可能明显影响可用内存。

但这要结合显示、摄像头、视频编解码等驱动需求，不能盲目关。

---

# 九、重点看 MemAvailable，不要只看 MemFree

64MB 下 `MemFree` 很低不一定代表异常，因为 Linux 会拿空闲内存做缓存。

真正关键是：

```bash
grep -E "MemTotal|MemFree|MemAvailable|SwapTotal|SwapFree" /proc/meminfo
```

如果：

```text
MemAvailable
```

长期只剩 1MB、2MB，说明系统真的没有可用内存了。

如果：

```text
MemFree = 1MB
MemAvailable = 8MB
```

那不一定严重。

---

# 十、判断是否还有 direct reclaim

执行：

```bash
grep -E "allocstall|pgscan_direct|pgscan_kswapd|pgsteal|pswpin|pswpout" /proc/vmstat
```

隔几秒再执行一次：

```bash
watch -n 2 'grep -E "allocstall|pgscan_direct|pgscan_kswapd|pgsteal|pswpin|pswpout" /proc/vmstat'
```

如果这两项涨得很快：

```text
allocstall_normal
pgscan_direct_throttle
```

说明进程正在自己回收内存，这就是卡顿主因。

优化目标是：

- `allocstall` 少涨；
- `pgscan_direct` 少涨；
- 回收更多由 `kswapd` 后台完成；
- `pswpin/pswpout` 可以涨，但系统不卡，说明 zram 在工作。

---

# 十一、如果还是卡：64MB 的现实结论

如果打开 zram、调高水线之后，`MemAvailable` 仍然长期低于 2MB～3MB，那基本不是内核选项能完全解决的了。

64MB 下需要进一步做：

1. **限制非关键服务内存**
   - 如果有 cgroup：
     ```text
     CONFIG_MEMCG=y
     ```
   - 给非关键进程设置 `memory.max`。

2. **减少常驻进程**
   - 关闭不必要的服务；
   - 减少 Java/Python/Node 等重运行时；
   - 嵌入式场景尽量用 C/C++/Rust/Go 轻量服务，或者 busybox 工具。

3. **减少内核内存占用**
   - 关闭不用的模块；
   - 关闭 debug；
   - 减少内核日志缓存；
   - 不使用 tracing/ftrace/lockdep 等。

4. **低内存主动杀进程**
   - 可以用 earlyoom、lmkd，或者自己写脚本：
     - `MemAvailable < 3MB` 时杀掉非关键进程；
     - `MemAvailable < 2MB` 时重启非关键服务。

5. **如果可能，加内存**
   - 64MB 跑完整 Linux 5.10 + 应用 + 文件缓存，本身就很紧张。
   - 如果有图形界面、数据库、Java、AI 推理、视频处理，基本不够。

---

# 十二、我建议你实际这样配

对于 64MB Linux 5.10，我会先这样：

## 内核选项

```text
CONFIG_SWAP=y

CONFIG_ZRAM=y
CONFIG_ZSMALLOC=y
CONFIG_ZPOOL=y

CONFIG_CRYPTO_LZO=y
CONFIG_CRYPTO_LZ4=y

# 如果有 MGLRU backport
CONFIG_LRU_GEN=y
CONFIG_LRU_GEN_ENABLED=y

# 关闭这些
# CONFIG_TRANSPARENT_HUGEPAGE is not set
# CONFIG_DEBUG_VM is not set
# CONFIG_PAGE_OWNER is not set
# CONFIG_KASAN is not set
# CONFIG_LOCKDEP is not set
# CONFIG_PROVE_LOCKING is not set
```

## zram

```bash
modprobe zram num_devices=1
swapoff /dev/zram0 2>/dev/null
echo 1 > /sys/block/zram0/reset
echo lz4 > /sys/block/zram0/comp_algorithm
echo 1 > /sys/block/zram0/max_comp_streams
echo $((24*1024*1024)) > /sys/block/zram0/disksize
echo $((12*1024*1024)) > /sys/block/zram0/mem_limit
mkswap /dev/zram0
swapon -p 100 /dev/zram0
```

## sysctl

```bash
sysctl -w vm.min_free_kbytes=2048
sysctl -w vm.watermark_scale_factor=200
sysctl -w vm.swappiness=80
sysctl -w vm.page-cluster=0
sysctl -w vm.dirty_background_bytes=1048576
sysctl -w vm.dirty_bytes=4194304
```

如果还卡：

```bash
sysctl -w vm.swappiness=100
sysctl -w vm.min_free_kbytes=3072
sysctl -w vm.watermark_scale_factor=300
```

如果更容易 OOM：

```bash
sysctl -w vm.min_free_kbytes=1024
sysctl -w vm.watermark_scale_factor=100
sysctl -w vm.swappiness=60
```

---

一句话总结：

> **64MB 内存下，最有效的不是单个“神秘开关”，而是：开 `CONFIG_ZRAM` + 设置合理 `min_free_kbytes/watermark_scale_factor` + 限制脏页 + 必要时开 MGLRU。**  
> 如果做完这些 `MemAvailable` 还是只剩 1MB，就必须限制进程内存或减少功能，否则内核层面很难避免卡顿。
